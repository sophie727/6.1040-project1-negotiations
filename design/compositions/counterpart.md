# The counterpart

At a practice table, the person negotiates against the counterpart: the AI, which takes every seat the person doesn't. The player `bot:counterpart` takes one of them, and at a scenario with more than two roles, [another counterpart takes each seat left](practice.md#starting-a-practice-table), so each seat the AI takes plays its own role from its own brief. As in conceptbox, the counterpart is an agent. Reactions here ask it questions with `Reasoning.prompt`, the agent answers through [the answering endpoints](reusable/answering.md), and reactions here apply its concluded answers. No reaction calls a model, and the agent changes nothing at the table directly; the reactions here decide what each answer does.

The agent in `src/agents/counterpart.ts` answers with a language model, Claude or Gemini, when the server has an API key for one. The model plays the role its brief describes: it reads the brief, the conversation, and each proposal's worth to its role, replies in at most three sentences, and decides on proposals. It reads only the brief of the role it answers as, so at a table with several counterparts, none of them learns what another's brief says. Without a key, and in the tests, a stand-in answers instead: canned replies, and an answer to each proposal that accepts it exactly when it is worth at least the role's BATNA. Either way, the reactions here are the same.

## Asking

[The roles the counterparts play at a table](view:counterpart.asking.counterpartRole) are the seats that AI counterparts have taken: those whose player [is a counterpart](computation:isCounterpart) rather than a person. The counterparts don't speak first: who opens, and whether to name a number first, is part of what the person practices, so they wait for them. When a person sends a message, a reaction [asks for a reply](reaction:counterpart.asking.AskForReply), and when a person proposes, a reaction [asks for a decision](reaction:counterpart.asking.AskForDecision). Neither asks while a question of the same kind [is waiting](view:counterpart.asking.hasWaitingQuestion) for the agent to take it. The agent reads the whole table when it takes a question, so one waiting question covers every message or proposal that came before it. A question the agent is already answering doesn't count, so a message that arrives while a counterpart is writing still gets its own reply. The counterparts' own messages and proposals ask nothing, so they never answer themselves.

Each question is about a table, not a seat, so the agent chooses which counterpart answers it, and the answer names that role on its first line. A person's message is answered first by the counterpart it asks a question of, or else by the one it names first, or, when it names none, by the one that has gone longest without speaking. At a table with more than one counterpart, the others may add to that reply. Once a counterpart's reply has been sent, a reaction [asks whether anyone else adds something](reaction:counterpart.asking.AskForFollowUp), unless that question is already waiting. It waits until the reply's flow has settled, so the next counterpart reads the reply in full. The agent answers as a counterpart that hasn't spoken since the person's message, or with PASS when every one of them has, or when the one it chose has nothing to add. Each reply asks again, so a person's message gets at most one reply from each counterpart, and the first PASS ends the round. At a table with one counterpart, nobody else could add anything, so the question is never asked.

A proposal needs an answer from every counterpart, and the agent answers a decision as the first counterpart that has yet to answer the waiting proposal. When a counterpart accepts a proposal that is still pending, and another counterpart [has yet to answer it](view:counterpart.asking.owesAnswer), a reaction [asks for the next decision](reaction:counterpart.asking.AskForNextDecision), unless one is already waiting. It too waits until the flow has settled, so each counterpart decides in turn, having read what the one before it said. A rejection from any of them rejects the proposal, so nobody else has to answer it.

```computations
isCounterpart(negotiator: String) : Boolean
  Whether a player at a table is an AI counterpart rather than a person: every counterpart's name starts with `bot:`, and no person's Registering user does.
```

## Starting

The counterparts have no brief to read, so they are always ready. When someone else suggests how long to negotiate, a reaction [agrees for every counterpart](reaction:counterpart.starting.AgreeToAnyStart) at once, so at a practice table the person's suggestion starts the clock. At a table with several people and a counterpart, the counterpart's agreement is one of those the suggestion waits for.

## Reading

The [read endpoint](reaction:counterpart.reading.ReadTable) starts with `AgentSessioning.use`, so a person's session is refused. It responds with [the table as each counterpart there sees it](former:counterpart.reading.tablesAsCounterpartsSeeIt): for each counterpart's seat, [the table as that role sees it](table.md#showing-the-table), with its own brief and BATNA, the conversation, and each proposal with its worth to that role and the roles that have accepted it so far, which is exactly what a person would see from that seat. The agent chooses the counterpart that answers from these, and the model reads only that one. The endpoint answers only for a prompt the agent took, matched through `Reasoning._taken`, so the agent can't read any other table. A prompt the agent didn't take is refused with `NOT_TAKEN`, and a table without a counterpart with `NOT_SEATED`. When the table is no longer open, the agent abandons the question with the reason "The negotiation is over."

```endpoints
counterpart.reading.ReadTable at /counterpart/table
```

## Answering

Every answer starts with the role that gives it, and the reactions here act only on an answer from a counterpart's role at the table. When the agent concludes a reply, or something a counterpart adds, a reaction [sends the rest of it as that role's next messages](reaction:counterpart.answering.SendReply), one per line, in order, as long as the negotiation is still under way. A PASS names no role, so it sends nothing and asks nothing more. The agent puts each paragraph on its own line, and splits a paragraph longer than the 2,000 characters a message holds, after its last sentence that fits, so a long reply arrives in parts rather than cut short or refused.

The answer to a proposal starts with three lines: the role, ACCEPT or REJECT, and the proposal it answers. What the role says about it follows, one message per line. The agent writes the proposal from the table it read, so each decision applies only to the proposal it was about. If the person replaced that proposal in the meantime, the old decision finds it no longer pending and does nothing, and the question the new proposal asked answers the new one.

A reaction [accepts the proposal](reaction:counterpart.answering.AcceptForCounterpart) when the answer accepts it, it is still pending, the role hasn't accepted it already, and `Briefing._dealPayoff` says it is worth at least the role's BATNA. Another reaction [rejects it](reaction:counterpart.answering.RejectForCounterpart) when the answer rejects it (the `decided` path), and also when the answer accepts a proposal worth less than the BATNA (the `below-batna` path). So no counterpart ever agrees to less than its alternative, whatever a model writes, and the person's offer is never left without an answer. The lines after those three [become the role's next messages](reaction:counterpart.answering.SayWhy), so the person reads why.
